# IMOSAE Source Lock
## Raw Japanese main-series release `IMOSAE-JP-LN-RAW-1.0`

## 1. Lock declaration

This document freezes the exact fourteen-file Japanese numbered light-novel corpus under the immutable source-set identifier **`IMOSAE-JP-LN-RAW-1.0`**.

The lock answers a narrow question: **what exact raw files govern the IMOSAE main-series analysis?** It does not claim that the Phase-0 normalized reading layer is finished. The normalized layer will receive its own derived-release identifier after gaiji handling, content classification, typography preservation, paragraph locators, and round-trip validation are complete.

Until superseded by an explicit later raw source generation, all main-series literary claims must ultimately trace to these locked files.

## 2. Authority boundary

### Included

- Japanese numbered light novels V01–V14 listed below.
- The prose, illustrations, afterwords, colophons, typography, and other paratext physically contained in those EPUB packages, with their content roles classified separately.

### Excluded from this raw lock

- translations;
- anime or manga adaptations;
- drama CDs / audio dramas;
- audiobooks;
- retailer-only or event-only short stories not contained in these EPUBs;
- the Kantoku art book;
- externally sourced interviews or promotional materials;
- extracted/normalized text generated by this project;
- any future supplemental acquisition.

Supplemental material must receive a distinct source ID and authority tier under `IMOSAE_SUPPLEMENTAL_SOURCE_INVENTORY_AND_ACQUISITION_PLAN.md`.

## 5. Immutability rules

### 5.1 Do not modify the locked EPUBs

The original EPUB bytes are immutable. Do **not**:

- rewrite OPF metadata;
- normalize filenames inside the archive;
- replace or recompress images;
- repair ruby in place;
- insert resolved gaiji characters into the EPUB;
- convert EPUB 2 to EPUB 3;
- strip promotional material;
- change line endings or container structure.

All analytical convenience transformations belong in a **derived layer**, never in the raw files.

### 5.2 A filename is not identity

Source identity is the tuple `source_set_id + SHA-256 + byte length`. A renamed copy with the same hash is the same locked source object; a file with the same visible filename but a different hash is **not** part of this release until audited and deliberately admitted.

### 5.3 Replacement copies create a new generation

If a better retail edition or demonstrably more faithful package is later acquired, do not silently replace a locked file. Create a new candidate source set, compare it against `IMOSAE-JP-LN-RAW-1.0`, document differences, and issue a new lock only if the project intentionally migrates.

Recommended next identifier if a raw migration ever occurs: `IMOSAE-JP-LN-RAW-2.0`.

## 6. Bibliographic authority

For project bibliography, **colophon data outranks embedded OPF metadata**. Embedded metadata remains provenance and retrieval metadata only.

This rule is necessary because package metadata is heterogeneous and at least one value is chronologically misleading (V03's package `dc:date` is later than its actual base publication), while V05/V07/V08 omit package dates. The colophons provide a coherent V01–V14 publication sequence and ISBN set.

The source lock therefore freezes both:

1. the bytes of each EPUB; and
2. the colophon-derived bibliographic interpretation recorded in `IMOSAE_SOURCE_INVENTORY.md`.

## 7. Raw source versus normalized reading layer

The locked EPUBs are the **ultimate primary evidence**. For efficient close reading, the project will generate a deterministic normalized layer. That layer is subordinate to the raw source and must remain reversible/auditable.

The future normalized layer must preserve at minimum:

- volume and spine order;
- XHTML/member identity;
- paragraph boundaries;
- base Japanese text;
- ruby base/readings as separable fields;
- gaiji via resolved character plus source-gaiji ID, or explicit unresolved token;
- analytically relevant emphasis/typography;
- illustration insertion anchors;
- content-class labels;
- stable paragraph/source locators.

No normalization decision may make it impossible to reconstruct where a passage came from in the locked EPUB.

## 8. Known normalization hazards under this lock

### Ruby

The corpus contains approximately **29,083 ruby constructions**. Naïvely extracting both `<rb>` and `<rt>` into the prose stream can duplicate readings and corrupt quotation/search behavior.

### Gaiji

The complete raw census currently identifies **651 inline gaiji occurrences / 65 distinct image hashes**. Naïve HTML stripping can delete them. This count supersedes the earlier preliminary estimate.

### Heterogeneous package paths

The set contains both EPUB 2/NCX and EPUB 3/nav packages, with multiple internal naming conventions. The normalization system may not assume one fixed OPF or XHTML path scheme.

### Mixed narrative and paratext

Afterwords, colophons, promotional matter, covers, digital bonuses, and other publication material share the EPUB spine with narrative material. Content-class typing must precede any corpus-wide literary search that claims to cover 'the novels.'

## 9. Permitted derived artifacts

Derived files are permitted and expected when they are clearly labeled as non-source transformations. Examples:

- normalized UTF-8 reading text;
- JSON/JSONL paragraph records;
- ruby sidecars;
- gaiji maps;
- illustration inventories/thumbnails generated for analytical navigation;
- locator indexes;
- chapter maps;
- evidence ledgers;
- analytical Markdown.

Each derived artifact must identify `IMOSAE-JP-LN-RAW-1.0` as its source boundary until a later raw lock explicitly supersedes it.

## 11. Change control

Any proposed change to this lock must use one of the following dispositions:

- `PRESERVE` — existing file remains authoritative;
- `STRENGTHEN` — additional provenance confirms it without changing identity;
- `REVISE` — source boundary or bibliographic interpretation changes;
- `DOWNGRADE` — file remains preserved but loses preferred authority;
- `REJECT` — candidate replacement/supplement is not admitted;
- `OPEN` — unresolved comparison remains pending.

A raw-byte change always requires `REVISE` plus a new source-set identifier; it can never be an in-place silent correction.
