# Manga / Anime Long-Series Hybrid Execution Protocol

> **Prefer fresh cloud architecture, local longitudinal analysis, fresh cloud retrospective synthesis, and local evidence completion and integration. Preserve continuity in the corpus, not in a single enduring conversation.**

This is the owner's preferred default for substantial long-series work. It is not a claim of experimentally proven optimality or a requirement to use every phase for a bounded task.

## 1. Scope and governing responsibilities

Use for long manga/LN runs, multi-season anime, substantial game narratives, and bounded live-service source tranches when sequential evidence accumulation and retrospective synthesis are distinct responsibilities.

The [initiation policy](MANGA_ANIME_PROJECT_INITIATION_AND_ARCHITECTURE_POLICY.md) owns the architecture gate. The [continuation policy](MANGA_ANIME_SEQUENTIAL_EXECUTION_SCOPE_AND_CONTINUATION_POLICY.md) owns authorized run extent and atomic-unit recovery. The [reasoning policy](MANGA_ANIME_REASONING_AND_MODEL_ROUTING_POLICY.md) owns model/class selection. The [topology policy](MANGA_ANIME_EXECUTION_TOPOLOGY_AND_CAPABILITY_ROUTING_POLICY.md) owns environment capability and role allocation. The [handoff contract](MANGA_ANIME_ANALYTICAL_HANDOFF_AND_INTEGRATION_CONTRACT.md) owns transfer and acceptance.

This protocol owns the phase sequence and readiness conditions. It neither creates a parallel entrypoint nor changes repository authority, curation ownership, source precedence, or frozen-history rules.

## 2. Preferred lifecycle

```text
Owner-authorized project / source reconnaissance
    -> fresh cloud Pro: framework and synthesis/corpus architecture
    -> local Work/Codex: architecture integration and initiation-gate verification
    -> local Work/Codex: sequential readings + synchronized ledgers + checkpoints
    -> local Work/Codex: frozen synthesis-input snapshot and readiness assessment
    -> fresh cloud Pro: monographs + specialists + retrospective synthesis
    -> local Work/Codex: required source/AV completion + semantic reconciliation
       -> if a central premise changes: bounded synthesis revision + dependent-specialist review
          -> return to evidence completion and semantic reconciliation
    -> local Work/Codex: repository validation and authorized integration
```

This describes execution ownership, not a requirement for one particular session or one combined delivery. A phase may use several bounded sessions. Multiple specialists may run against one snapshot when their targets are separate and a convergence owner is named.

| Phase | Preferred owner | Exit condition |
|---|---|---|
| Architecture authorship | Fresh cloud Pro; local also permitted | Complete method/architecture proposal with explicit responsibilities and source limits |
| Architecture integration | Local Work/Codex | Current eligible foundation, required infrastructure, and truthful initiation state |
| Sequential accumulation | Local Work/Codex | Each authorized unit transaction closed; ledgers and high-water mark synchronized |
| Synthesis readiness | Local Work/Codex | Scoped, versioned, retrievable evidence state and named targets |
| Retrospective synthesis | Fresh cloud Pro | Substantial evidence-grounded outputs, counterreadings, limitations, and return receipt |
| Evidence completion and convergence | Local Work/Codex by default | Required channel debts and cross-document contradictions resolved or explicitly bounded; any reopened synthesis and affected dependencies reviewed before acceptance |
| Publication | Authorized local repository operator, with specialized maintenance owners | Applicable checks and exact-commit integration requirements satisfied |

A preferred owner is not automatically an authorized executor. The current instruction must cover the actual work, source boundary, and writes. A next-phase label is routing information, not permission to begin unrequested work.

## 3. Architecture authorship: fresh, but informed

Prefer a fresh cloud Pro session supplied with the canonical root or new-root authorization, current governance, available source inventory, source-language/edition information, known analytical objectives, existing project material, and constraints.

Architecture need not wait for complete acquisition. It does need enough reconnaissance to select appropriate units, evidence channels, prospective rules, and cumulative responsibilities. Uncertainty should remain visible. Do not use later plot knowledge or outside series summaries to solve design uncertainty when the prospective boundary excludes them.

The proposal must establish the paired responsibilities of an analytical/deep-reading method and a synthesis/corpus architecture. Preserve the initiation policy's allowance for a coherent combined document in compact or mature projects; do not require an arbitrary document count.

Define how primary-source observations feed justified ledgers, checkpoints, claim revision, mature character/relationship work, specialist synthesis, and eventual convergence. Identify required versus optional evidence channels and day-one infrastructure. Do not manufacture empty ledgers for visual symmetry.

For long projects, assign phase owners and the intended synthesis handoff boundary. Define the questions a major monograph or specialist must answer so that later prose cannot pass merely by having the right filename.

## 4. Architecture integration before sequential reading

The local integrator reconciles the proposal with live governance and existing project architecture, checks exact paths and artifact identities, establishes only authorized infrastructure, and performs the applicable repository checks.

The project may perform bootstrap and reconnaissance while `SEQUENTIAL_ANALYSIS_LOCK = CLOSED`. It may not begin its first governed substantive sequential reading until the existing initiation gate is genuinely satisfied and the canonical entrypoint records OPEN.

A cloud proposal, created directories, a generated outline, or the availability of source files is not gate satisfaction. Keep the existing machine gate, activation baseline, legacy compatibility, and material-restart semantics unchanged. This protocol creates no new automatic exemption or enforcement schema.

## 5. Sequential accumulation: local Work/Codex

The local sequential owner handles primary sources, extraction/inspection routes, source locks, ordered readings, and the longitudinal infrastructure specified by the architecture. It owns ordinary Git operations for this run subject to live controls.

Each source unit must close as a complete transaction: reading, applicable ledger and claim updates, locators, prospective entering/exiting state, current-state advancement, and the required persistence/verification. Do not queue ten readings and postpone every ledger update to the end merely to reach the cloud phase sooner.

Follow `single_operation` or explicitly authorized `continuous_sequential`. The terminal boundary, committed high-water mark, next candidate, and interrupted work must remain distinct. A run across many units must not admit later evidence into earlier prospective freezes.

Checkpoints belong near the active evidence state and are usually local. Exceptionally difficult phase-boundary adjudication may use fresh cloud review against a frozen snapshot, with local reconciliation before continuation if it changes load-bearing state.

No session is required to remain alive for the entire run. Close and verify a coherent unit, externalize state, and start a fresh session when needed. Repeated name corruption, lost source distinctions, inconsistent high-water marks, or unsupported claims of tool use are reasons to pause and verify, not to trust accumulated familiarity.

## 6. Synthesis readiness is a separate gate

Before a cloud synthesis assignment, the local owner provides a bounded input snapshot and assesses whether the requested responsibility is supportable.

A suitable readiness record identifies:

- exact Git commit/branch and canonical entrypoint;
- authorized source boundary, editions/continuities, and relevant knowledge cutoff;
- completed sequential unit coverage and known omissions;
- current eligible ledgers, checkpoints, revision state, and source routes;
- intended artifact IDs, canonical paths, scopes, and role-specific acceptance criteria;
- unresolved disagreements, translation questions, and evidence/capability limitations;
- named integration owner and any mandatory later stage.

Use a boundary such as volumes 1-11 or a specific locked event inventory, not an unqualified claim of full-series completeness. Source content existing locally is not the same as that content having been read. Ledger presence is not proof of adequate analytical coverage.

Missing evidence should be classified. A material absence may block the target; a bounded omission may support a scoped provisional synthesis; an optional enrichment may remain open. Do not block all useful synthesis solely because the entire franchise is unfinished. Do not silently call a partial source boundary the full franchise.

## 7. Fresh cloud synthesis bootstrap

Fresh context means a new working context initialized from durable evidence state. It is not a blank slate, a claim of unbiased reasoning, or permission to rely exclusively on a short previous-session summary.

Supply or provide verified routes to governance relevant to the assignment, the current entrypoint, method/architecture, target-specific ledgers, checkpoints, sequential readings, claim revisions, source locators, and unresolved questions. Resolve character identity through the existing registry where applicable; do not invent new IDs from name similarity.

Use tiered retrieval rather than indiscriminate loading. Read the governing state and target contract first, then the relevant longitudinal structures, then the readings and primary witnesses needed for the actual argument. The output must disclose material inaccessible inputs and partial coverage.

A generated evidence summary can orient the analyst but cannot be the sole support for conclusions that depend on distinctions it omitted. Retrieval of a file does not prove that its contents were completely inspected. Conversely, a mature corpus does not require rereading all raw sources as a ritual before every synthesis.

## 8. Cloud analytical responsibilities and depth

Cloud Pro is tasked with substantial analytical authorship, not merely formatting local findings. Its deliverable can be a complete monograph or synthesis within the assigned evidence scope.

For a major character, the architecture should normally make development/state transitions, motive and self-report, relationship conditioning, language/performance where supported, contradictions/counterevidence, thematic function, and limitations recoverable. The actual work determines which dimensions matter; do not force every character through an identical psychological template.

A specialist must make an argument appropriate to its role. A continuous synthesis must reconcile specialist findings into a coherent account rather than concatenate abstracts. A reconstruction model remains distinct from literary interpretation and must meet its own behavioral constraints and validation responsibilities.

Do not impose a universal word ceiling. Evaluate whether the output preserves the significant evidence, competing readings, transitions, and explanatory mechanisms warranted by its scope. A short outline is not a mature monograph because it uses the correct headings; an expansive document is not adequate merely because it is long.

The cloud analyst can challenge local interpretations. Record proposed changes with evidence and claim transitions; do not silently rewrite frozen sequential documents or shared live ledgers. Supported existing work should be preserved, but no inference is immune to source-grounded correction.

## 9. Split multimodal completion

When text and a verified audio route are accessible in cloud but required large-video inspection is not, assign the cloud stage a text/audio responsibility and the local stage the unresolved visual/temporal responsibility.

An illustrative character case such as Sigrika is a workflow example, not a claim that her source corpus has already been read. The transfer identifies inspected sources and audio tracks, remaining video objects/intervals, claims needing validation, and possible falsifying observations.

The local pass must examine whether staging, facial/body performance, editing, camera position, and sound-image timing preserve, qualify, or contradict the text/audio interpretation. It must not assume visual confirmation in advance or treat AV as decorative enrichment.

Local ownership does not guarantee an adequate AV route. Verify actual inspection capability under the topology policy. If a mandatory route remains unavailable, preserve bounded completed work and report the unresolved claim/debt. Use targeted evidence where sufficient and full-source continuity when the question requires it.

Do not make AV completion mandatory for prose-only analysis or for an explicitly text-scoped artifact whose governing method does not require it. Evidence requirements come from the artifact's analytical responsibility, not from the mere existence of a video.

## 10. Convergence and final integration

The local integrator checks exact delivered bytes, declared scope, required-channel coverage, source locators, new claim revisions, conflicts with other specialists, and loss of existing analytical detail. A repository test pass alone cannot establish semantic quality.

If source or AV completion changes a central premise, reopen the affected monograph or synthesis before final semantic acceptance. Record the changed premise, supporting and counterevidence, affected claim IDs or sections, and dependent specialist or convergence artifacts. Assign a bounded revision to an adequate authorized analyst; fresh cloud Pro remains the preferred owner for substantial synthesis revision, with local integration afterward.

Recheck each identified dependent artifact for consequences of the revision, then return the revised candidate to evidence completion and semantic reconciliation. Repeat only the affected work until the revised argument and its dependencies meet their declared acceptance criteria. Preserve unaffected analysis and prospective freezes. A changed central premise cannot be closed merely by appending an AV note or marking the inspection complete. If the necessary revision exceeds existing authorization or source scope, record the precise remaining requirement and hold acceptance of the affected scope pending direction.

Apply supported corrections to the existing topical homes and revision infrastructure. Preserve historical freezes and truthfully distinguish retrospective amendments from what was knowable earlier. Do not rewrite the entire corpus to synchronize a new interpretation.

Preserve useful cloud prose unless evidence, scope, structure, or a demonstrable defect warrants a change. When restructuring, retain the reasoning and evidence rather than reducing a substantial synthesis to a generic summary. Record consequential changes and unresolved disagreements in the appropriate project home.

A fresh final cross-specialist audit may be commissioned when the integration problem is unusually broad. It can run in cloud and return findings to the local operator. Publication ownership need not dictate where every intellectual audit occurs.

Promotion follows existing authority and eligibility rules, not a new automatic lifecycle. Stage completion, analytical readiness, successful validation, branch publication, and integration into current authority are separate facts.

## 11. Scoped parallelism and moving branches

Distinct monographs may be assigned to separate fresh cloud sessions at one frozen boundary. Assign unique output paths and prohibit concurrent edits to shared ledgers and the current entrypoint. The integrator owns reconciliation of overlaps and updates to shared state.

Local sequential work may continue beyond the synthesis boundary when authorized, but the cloud draft remains tied to its dispatched snapshot. New evidence cannot silently enter a through-volume-11 monograph merely because the branch now contains volume 12. Decide whether to publish a bounded result, request an authorized extension, or defer integration pending material reconciliation.

Novel later evidence does not invalidate useful earlier analysis automatically. Equally, a newer branch must not be overwritten with a stale snapshot. The handoff contract's base/candidate/current comparison controls acceptance.

## 12. Adoption for existing projects

Introduce the topology at the next appropriate boundary without restarting completed readings. An active project can hand a closed tranche to cloud synthesis while preserving its existing root, ledger design, naming, and historical interpretations.

A thin existing monograph can undergo an authorized deepening pass against mature evidence without rerunning the sequential phase. Architecture gaps require explicit repair under the initiation policy, not cosmetic scaffolding. This protocol does not itself authorize a material restart.

Record the adopted topology and stage ownership once in the existing entrypoint or governing architecture. Use the handoff template only where a real transfer warrants it. Do not create permanent handoff documents for every trivial internal action.

## 13. Failure and stopping behavior

Stop the affected operation on unresolved authority, source-boundary conflict, required evidence/capability failure, stale conflicting state, or unverified transfer integrity. Continue independent authorized work when it can remain valid.

A failed connector does not authorize reconstructing missing files from memory. A new session does not confer additional source access or extend the authorized run. A polished candidate does not become canonical because the receiving session ran out of context.

For long interrupted work, recover the verified current state before resuming. Prefer completing a coherent unit before handing off, but never conceal partial completion. The existing continuation policy remains authoritative for recovery and stop semantics.

## 14. Success criteria

Evaluate the topology by evidence-grounded analytical depth, preserved prospective boundaries, low transfer loss, accurate names and locators, useful counterreadings, bounded unresolved debt, non-regressing project state, and reduced avoidable integration/rework cost. Resource efficiency matters only alongside these requirements.

The default may be changed for a task when another adequate route is better. Record the reason; do not convert a situational exception into a claim that cloud or local is categorically superior.
