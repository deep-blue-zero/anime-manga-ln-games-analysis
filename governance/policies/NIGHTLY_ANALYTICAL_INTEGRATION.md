# Nightly analytical integration

The owner-operated EC2 CI and PR Integration Steward is the repository's primary autonomous PR reconciliation and integration coordinator. `.github/workflows/nightly-integration.yml` and its bound `tools/nightly_integration.py` controller are retained as an owner-invoked manual fallback for mechanical integration of audited `series/<stable-slug>` and `studies/<stable-slug>` branches. The fallback has no competing scheduled integration authority and gains no interpretation, character curation, governance-change, conflict-repair, or temporary-branch integration authority.

The workflow is manual-only: its sole trigger is an owner `workflow_dispatch` on `main`, and the CLI independently rejects scheduled or non-owner fallback apply. It uses the same reviewed controller and shared lock as the primary EC2 route. `NIGHTLY_INTEGRATION_ENABLED=false` keeps fallback writes disabled. The additional live repository variable `INTEGRATION_EXECUTOR_MODE` must equal `fallback` for fallback apply or `primary` for primary apply; absent, unreadable, `disabled`, and all other values prohibit apply. Changing these settings, installing the EC2 service or issuing credentials remains an owner deployment operation after protected review. Merging this implementation does not activate either route.

## CI and PR Integration Steward

The owner grants an owner-operated, scheduled EC2 agent standing authority to act as the primary autonomous CI and PR Integration Steward: diagnose and remediate routine CI failures, reconcile technical conflicts, synchronize authorized source branches with current `main`, and integrate eligible owner-authored PRs through a trusted deterministic controller. Eligible operations need no repeated owner approval per PR. This delegation is part of the existing owner-controlled integration process; it creates no separate analytical, curation, or governance authority.

### Eligibility and reserved decisions

Eligible PRs are open, owner-authored, same-repository PRs targeting `main`, with approved commit identities and a verified bounded delta. Approved source categories are continuing `series/<stable-slug>` and `studies/<stable-slug>` branches within their existing analytical boundaries, and narrowly named temporary `codex/<purpose>`, `chatgpt/<purpose>` or `claude/<purpose>` branches for routine cross-cutting documentation or deterministic routing outside the reserved path classes below. Tooling, workflow, validation and control changes, including CI repairs to them, are reserved. Assess the complete PR and proposed repair, not merely the branch name, title, label, or a passing check. No external PR, patch import, arbitrary branch category, or unrelated analytical payload is admitted.

Draft state and the `nightly-hold` PR label are the only hold signals, and both are binding for maintenance publication and integration. An owner hold expressed anywhere else takes effect only once it is recorded as one of them. Only the owner releases a hold, by marking the PR ready or removing the label outside any steward or executor cycle; neither the steward nor the executor ever performs either operation. The executor reads both signals at every capture and immediately before merging, and a hold seen at any point in a cycle blocks that PR for the whole cycle. Otherwise eligible intermediate analytical publications may integrate without a new opt-in label, per-PR owner confirmation, terminal project completion, or invented completeness hold. Existing source, initiation, handoff/semantic acceptance, publication, and validation requirements still apply; technical integration does not certify interpretive completeness or promote a noncurrent draft.

Because the steward acts with an owner credential, no label, comment, review, status or PR state that credential can create is evidence of owner approval. Reserved work is therefore enforced by path: the executor computes the complete changed-path set of the final head against current `main` and refuses routine integration when any path is under `.github/`, `tools/`, `crosswalk/` or `provenance/`; is under `governance/` other than `governance/MANGA_ANIME_CORPUS_INDEX.md`; is `characters/README.md` or `characters/RECONSTRUCTION_CAPABILITY_SPEC.md`; or is the root `AGENTS.md`, `LICENSE.md`, `THIRD_PARTY_NOTICES.md`, `CONTRIBUTING.md`, `.gitattributes` or `.gitignore`. Separate owner approval of reserved work is evidenced only by the owner performing that protected merge personally, outside the steward and executor. This path rule is a floor: the steward's judgment may reserve more, never less.

Separate owner approval is required for authority-scope/epoch changes, changes to governance or enforcement semantics, security-sensitive changes (including credentials, access, workflow privileges, validation/publication protections or controller trust), changes to authorized source boundaries or rights, and substantively ambiguous modifications. Existing authorized source admission within those boundaries needs no new steward-specific approval. A technical-looking failure cannot justify weakening a check or manufacturing a green result. The steward may diagnose and propose such work, but must not author or integrate it under routine delegation. This includes amendments to its own authority. Clearly mechanical documentation corrections do not become authority changes solely because of their path.

The character curation agent remains the sole routine writer of `characters/registry.jsonl` and `CHARACTER_ANALYSIS_INDEX.md` and retains its independent `character-registry` integration route. The steward may preserve/import verified curation commits and integrate an otherwise eligible analytical PR containing a separately identifiable, curation-agent-authored repair under the existing policy; it may not curate, regenerate those files, or substitute its judgment for the curator. The reconstruction evaluator likewise remains the sole routine writer of `characters/reconstruction_capabilities.jsonl` and `characters/CHARACTER_RECONSTRUCTION_INDEX.md` under `CHARACTER_RECONSTRUCTION_MAINTENANCE.md`; `character-reconstruction` is not an eligible source category, and the steward never writes or regenerates those files. Housekeeping retains its exact five-output ownership. On stable branches the steward supplies declarative inputs or imports verified outputs, leaving regeneration to housekeeping; routine cross-cutting generation follows the checklist and designated generators.

### Reconciliation and shared integration invariants

Both the primary steward path and the manual fallback must enforce the source-preservation, publication, exact-head certification, protected-merge and post-merge invariants below through an independently enforcing deterministic integration executor. The fallback additionally retains its narrower candidate and clean-merge contract in the next section. The steward's eligibility judgment or a repair receipt is input to verification, never a substitute for executor enforcement. Independent CI auditing, housekeeping and character curation retain their existing contracts and ownership.

1. Read live governance, capture current source and main heads, review the complete delta and any CI failure evidence, and coordinate source publication with the author, housekeeping and any curation repair. Require a successful starting-main audit and verified owner-only access before remote mutation, using the access preflight in the fallback contract below. Preserve all intervening work. Repairs must stay within the PR's authorized purpose and exact declared paths; substantive interpretation or unresolved provenance goes to the owner.
2. Prepare targeted technical repairs or an ordinary reconciliation merge on the authorized source branch. Apply the checklist's squash-merge reconciliation proofs, including full prior source/integration tree comparisons and review of both sides since that baseline. Resolve only evidence-supported technical differences; never choose whole-file `ours`/`theirs` without proof, rewrite history, rebase published work, or force-push. Record the preservation evidence and repair rationale in the existing PR/operation receipt.
3. Run the applicable local checks against the entire final candidate, including the full gate for executable validation, workflow, schema, publication-safety or authority controls. Reread live provider rulesets, both remote heads and hold state immediately before publication; reconcile and repeat affected checks on drift. Publish only verified ordinary non-forced source commits under approved identities and read back the exact resulting tree and changed paths. Publication safety applies before every push. Failed CI permits diagnosis and bounded repair, never integration of the failing head.
4. Complete the existing source-audit/housekeeping/final exact-head sequence for stable analytical branches. Routine cross-cutting PRs require the full repository audit on their exact final head without routing deferral. A successful trusted `Repository integration audit` for the actual final SHA is mandatory; missing, pending, failed, skipped, cancelled, superseded or unrelated results cannot authorize integration.
5. Only a reviewed trusted deterministic integration executor, running trusted code independently of candidate content and enforcing gates independently of the steward, may perform merges through either path. Keep merge/write credentials out of candidate execution. The controller must independently enforce owner-only access, PR/branch/path eligibility, reserved-decision exclusions and explicit holds, current-main ancestry, both expected heads, trusted exact-head audit provenance, the live no-bypass strict main and activation-tag rulesets, and required reviews. Use the protected PR endpoint with the exact expected head and squash merging under required linear history. No direct main push, protection bypass, auto-merge shortcut, or agent-discretionary merge command is authorized.
6. Apply the existing mandatory post-merge contract: immediately record the integration SHA, compare its entire tree with the final audited source, dispatch `audit-generated-commit` for that exact main commit, and wait for a fresh successful owner-dispatched full audit with the existing status-watermark/provenance checks. A failure or timeout means integrated but unverified and halts further merges; repair forward through the existing process. Retain continuing branches and prune temporary branches only after the branch policy's exact preservation and green-main proof.

### Coordination and implementation boundary

Serialize steward runs and enforce one shared exclusive integration mechanism across the primary executor and manual fallback for the full capture/reconcile/publish/merge/post-merge-audit cycle. Both paths must refuse apply without verified exclusive ownership; ownership must remain enforceable at each mutation, including when a prior runner stalls or loses its lease. They must never merge concurrently. Separate local locks, time offsets, or the fallback workflow's existing scheduler-only concurrency group are insufficient. Recheck both heads throughout; exclusion never replaces server-side protection.

Fallback apply requires an explicit owner invocation, a paused and drained primary executor, and the same shared exclusion and integration invariants. Do not automatically promote fallback into another scheduler or use it to evade a failed primary gate. Before resuming primary operation, drain any fallback apply and release its ownership. Coordinate source writes, housekeeping, and independent curation integration without taking over their authority; if exclusive integration cannot be established, defer apply. Unexpected source updates require reconciliation and revalidation, and external main/control changes stop the current cycle under the existing contract.

The standing delegation grants authority, not deployment: it does not itself install EC2, a schedule/service, credentials or provider settings. The reviewed implementation below supplies the shared executor and manual-only fallback, while activation still requires an isolated trusted runtime, narrowly scoped owner credentials, verified shared exclusion, durable receipts, bounded failure reporting and an owner-controlled disable path. Preserve the independent CI reporter, housekeeping and character-curation contracts. Workflow/controller changes require hash bindings, focused regressions, full validation and protected integration; a new workflow still needs its own reviewed amendment. The standing grant supplies routine operational approval after those controls exist; it is not evidence that either path is deployed or activated. Neither path may apply under this role until shared exclusion is enforced.

### Executor implementation and shared ownership

The implementation following the standing grant extends `tools/nightly_integration.py` with `--role primary` and `--role fallback`. Both roles independently enforce live access, protected rulesets, approved source commit identities, reserved-path exclusions, observed holds, exact source/main heads and trusted audit provenance. Loaded controller and lock-module bytes must match their reviewed bindings on integrated `main`; an unmerged candidate cannot run apply using its own proposed bindings. Candidate Git objects are inspected in a separate bare object store and never checked out or executed with write credentials. The primary permits existing owner-authored temporary PRs only for root Markdown documentation and the five deterministic routing outputs outside reserved paths. Existing topology/validation further bounds those files. It never routes analytical payloads or either character branch through that category. The fallback remains stable-only. Both perform only clean stable-branch reconciliation; textual repairs and stale temporary PRs require author reconciliation and renewed certification.

`tools/integration_lock.py` uses the single coordination ref `refs/heads/integration-executor-lock`. This ref is infrastructure state, never an integration candidate or analytical branch. The executor may create it and advance it through single-parent, non-forced commits that retain the original tree and store only ownership metadata in their messages. It must never merge, delete, force-update or use this ref to publish corpus changes. GitHub's atomic ref creation and fast-forward checks choose one claimant when claims compete. A released state can advance to a held state for a unique run; only that run may advance it to released. No additional workflow, database, repository ledger file or expiring lease is introduced.

Ownership covers the operative inventory capture, reconciliation, source publication, PR creation, merge and exact-main audit. Each corpus/PR/audit mutation rechecks lock ownership, live enable mode and access/protection; observed holds remain binding for the entire run. A normal completed scan releases the lock, including candidates definitively blocked before integration. An unhandled failure, uncertain mutation, crash, cancellation, run deadline or failed post-merge audit retains the held state. A bounded candidate check timeout before integration may be recorded as blocked and the completed scan released when no write remains uncertain. There is no expiry, heartbeat-based takeover, automatic reset or force-unlock command: a stalled process can reduce availability but cannot overlap a replacement writer after a lease expires. Report the ownership commit/run ID and any already integrated SHA before stopping. Preview never acquires or mutates the lock.

The lock is not a credential boundary against the owner or another actor that can arbitrarily rewrite repository refs. Deploy the executor in an isolated owner-controlled runtime; the reasoning agent and candidate validation jobs must not possess its credential or modify its installed code. Ordinary agent instructions, labels or repair receipts cannot bypass its checks. Manual lock recovery is reserved to the owner: pause both entry points, terminate/drain the previous executor, revoke its write credential if its termination cannot be proved, resolve all in-flight/ambiguous GitHub outcomes, and verify any integrated main audit. Only then may a separately reviewed recovery advance the exact held ref to a released state without force or deletion. A missing lock during ownership, foreign/malformed state or unexpected ref change is a stop, not evidence that recovery happened. Initial creation is allowed only for a never-initialized ref; operators must never delete an established ref, since absence cannot distinguish first deployment from out-of-protocol deletion. Never reset ownership while the previous process or its requests could still write.

For a normal handoff, pause the primary scheduler, let its active run finish and release ownership, then set the live mode to `fallback` and explicitly dispatch the manual workflow. The shared ref independently refuses fallback while primary ownership is still held. To resume primary, drain fallback and observe released ownership before setting mode to `primary` and resuming the scheduler. To stop writes, set mode to `disabled`; the next mutation refuses and an interrupted cycle may require the recovery procedure above. Do not flip modes as a substitute for draining ownership.

## Candidate and integration contract

This section governs the narrower manual fallback; it adds no scheduled integration authority.

1. Capture the current main commit and a complete, sorted inventory of stable analytical branch names and tips. Automatically consider audited branches; no opt-in PR label is required. An existing draft PR or the `nightly-hold` PR label defers that branch. Authors must use one of those holds when published, structurally valid work should not yet merge. Structural checks do not determine whether interpretation is complete.
2. Confirm owner-only write access before any remote mutation: the collaborator list (all affiliations) contains only `deep-blue-zero`, no repository invitation is pending, and every deploy key is read-only. Apply halts when access is wider or any of the three lists is unreadable. Preview records `VERIFIED_OWNER_ONLY`, `NOT_OWNER_ONLY` with counts, or `UNVERIFIED` and continues, because it makes no writes. Require a successful starting main audit before any remote mutation. Require a successful source audit run; an authored-content run with a pending integration status permits reconciliation only. Missing, failed, cancelled, skipped, untrusted, or superseded audits never permit merging. Audit status must originate from the fixed GitHub Actions reporter and identify the approved audit workflow.
3. Verify the full source delta is confined to its named analytical root, the five housekeeping outputs, and any already agent-authored two-file character repair. Cross-cutting branches, `character-registry`, forks, and arbitrary branch names are excluded. The curation task retains its existing independent integration authority and schedule.
4. Incorporate current main through a clean Git merge on the existing source branch when needed. Construct the merge in a separate bare Git object store without checking out or executing candidate code. Preserve authored bytes through Git's clean merge; any textual conflict, including a generated-output conflict, defers the branch. No automatic conflict resolution, content rewriting, rebase of source history, force-push, or branch deletion is allowed. The reconciliation commit uses the existing approved owner author identity and GitHub committer identity.
5. The non-forced reconciliation push uses the owner credential so the existing owner-gated source audit and housekeeping sequence runs normally. Only the unchanged expected source or its one verified housekeeping child may advance the candidate. That child must have the exact parent, `Generated-From` trailer, approved identities, and a nonempty delta confined to the five generated routing files. Any other concurrent update defers the source.
6. Require the final source commit's successful `Repository integration audit` from the full audit dispatched by housekeeping as `github-actions[bot]`. Recheck current-main ancestry, the complete path boundary, both remote heads, and PR draft/hold state. A green author preflight or an unrelated manual audit is insufficient.
7. Create or reuse one owner-authored PR to main. Merge using the exact expected head through GitHub's protected PR endpoint. Read active repository ruleset `25199066` for exactly `refs/heads/main`, with no exclusions or owner/admin bypass actors, deletion/non-fast-forward prevention, required linear history, and strict up-to-date `Repository integration audit` from GitHub Actions app `15368`. Missing or redacted bypass data is unverifiable and stops apply. Use squash merging under this required linear-history rule. Do not enable auto-merge, bypass protection or required reviews, directly push main, or delete branches. Recheck the ruleset detail and enabled squash method before each merge.
8. Record the returned integration commit immediately. Compare its entire tree with the final audited source, explicitly dispatch `audit-generated-commit` for that exact main commit, and wait for a new successful owner-dispatched full audit. This dispatch is mandatory even if the owner-token merge also starts a push audit. If post-merge validation fails or times out, report the change as integrated but unverified and stop further merges. Do not automatically revert or rewrite main.
9. Process subsequent sources against the newly verified main. A source update is deferred; an external main update or control change stops the run. The installed workflow concurrency serializes its runs only; authorized manual apply additionally requires the shared exclusion and drained-primary conditions above. Repeated head checks and strict server-side protection remain mandatory for other writers. Ambiguous mutations are read back before deciding their outcome; the controller does not blindly retry writes.

Post-merge tracking examines the exact integration commit's audit-status history after the pre-dispatch status watermark. A later successful push audit must not hide the newest trusted owner-dispatched audit. The newest overall status must still be a trusted success; a failure halts and a pending result waits. The newest qualifying dispatch must itself have succeeded, so an older successful dispatch cannot conceal a failed, cancelled, or unfinished replacement. Workflow identity, reporter identity, owner actor, exact-commit status placement, and freshness remain mandatory.

When a source has no successful audit yet, apply may wait for its latest already queued or running owner-triggered push audit in the approved workflow, bound to the captured branch, exact commit, and repository. This read-only wait rechecks both heads and shares the existing 70-minute source/housekeeping budget and overall run deadline. Missing, untrusted, or terminal unsuccessful runs block without waiting; completion still requires the trusted reporter status and successful audit run before reconciliation. Preview reports the current deferral immediately. Waiting never certifies a commit, starts an audit, or relaxes the final housekeeping and protected-merge gates.

An already preserved branch or a clean combined tree identical to main produces no commit or PR. Partial success is preserved if another branch fails. Per-branch failures are reported and other eligible branches may continue; shared access errors and post-merge failures halt the run. Waiting is bounded by a 165-minute controller budget within a 180-minute job timeout, with at most 70 minutes for a source's audit/housekeeping sequence and 30 minutes for each explicit post-merge audit. The manual fallback may defer remaining work when its time budget expires.

If a merge conflicts, the controller may verify that the exact source tip was already preserved by an owner-authored, same-repository merged PR from that stable branch to `main`. It requires the PR's exact head SHA, an integration commit reachable from captured current `main`, and equality of the complete source and integration trees. Both remote heads are rechecked before reporting `already_integrated`, with the prior PR and integration SHA recorded. This read-only recognition handles squash-history conflicts after later changes to `main`; it performs no reconciliation, commit, push, PR creation, or audit dispatch. A newer source tip, unequal trees, unmerged PR, or integration outside current main's history cannot satisfy the proof. Git execution and API failures still fail; unresolved content conflicts still defer. Author publication and manual squash reconciliation follow `CHANGE_INTEGRATION_CHECKLIST.md#stable-analytical-publication-sequence`.

## Credentials and activation

These credentials and activation steps apply to the manual fallback, subject to the shared invariants and transition restrictions above.

Use a fine-grained token issued by `deep-blue-zero`, restricted to this repository, stored as the Actions secret `NIGHTLY_INTEGRATION_TOKEN` for fallback and supplied as `OWNER_TOKEN` only to the isolated primary executor. Required repository permissions are Contents read/write, Pull requests read/write, Actions read, Commit statuses read, Variables read (for the live enable/handoff controls), and Administration read (to inspect pending invitations and deploy keys). Metadata read is implicit and supplies the ruleset-detail reads; those responses must expose the no-bypass state for verification. No administration write permission is needed. Do not place the token in repository files, PR text, logs, or chat.

The owner credential is intentional: housekeeping accepts owner-originated pushes and the corpus audit retains its existing owner-author identity contract. The default `GITHUB_TOKEN` remains read-only and powers preview. The owner credential is supplied only to the trusted default-branch controller step. It is never passed to candidate validation code; all full audits run in the existing separate workflow. Token expiry or missing access is an actionable failure, not permission to fall back to a different identity.

The owner-authenticated protection check on 2026-09-05 found administrator enforcement and required linear history enabled, with force-push and deletion disabled, but no required status checks configured. That dated classic-rule observation is historical evidence, not the current operational check. The controller now reads `rulesets/25199066` during apply preflight and immediately before each merge, verifies all ruleset requirements in step 7, and refuses apply when they are absent or unverifiable. It does not fall back to the classic endpoint. The classic rule remains outside this code migration and may coexist with the ruleset; no settings change or deletion is authorized here. Activation-tag ruleset `21946617` and the publication policy's fresh tag-protection verification remain required. Any additional required human reviews remain effective.

After the owner reviews and personally protected-merges this implementation and verifies its main audit, deploy the exact reviewed controller and lock module from an immutable trusted checkout. The primary requires Python 3.11 or newer, a compatible current Git, GitHub network access, its separately provisioned owner credential, and a durable receipt directory outside disposable checkouts. An owner-managed EC2 scheduler can invoke `python tools/nightly_integration.py --role primary --mode apply --state-dir <durable-state-directory>` every eight hours; optional `--branch` bounds a smoke run. The executor validates that its installed code matches integrated main before acquiring ownership. Do not run it from a candidate worktree, expose its token to the reasoning agent, or dynamically install candidate dependencies.

Keep mode disabled and fallback disabled while deploying. Run primary and manual fallback preview, verify the exact workflow/controller/module bindings, access, rulesets and credential scopes, then select one route for a bounded owner-observed apply smoke test. Verify the coordination ref's claim/release transitions, contention rejection, protected merge and exact post-merge audit before unattended operation. Automated local/CI regressions exercise contention, stalled and lost owners, ambiguous outcomes, holds and failure retention; they are not claims of live deployment validation. The old cron is removed, not merely switched off. Preview makes no GitHub writes, publishes no branches or PRs, and does not claim that live protected merging or shared exclusion has been tested.

## Reporting and maintenance

The Actions step summary and JSON in the run log record the access check, source/base/final/integration SHAs, PR numbers, and candidate outcomes. The local report file is disposable; the GitHub run is the durable receipt. In preview, expected candidate deferrals (including missing or failed audits, holds, source drift, scope violations, and merge conflicts) produce warning annotations and a successful run when the scan completes. The report retains each blocked outcome and reason. Git execution errors, API/access errors outside the step-2 access check, and other run-halting failures still fail preview; an unreadable access check is recorded as `UNVERIFIED` instead. In apply mode, blocked work and failures continue to produce an unsuccessful run for normal Actions failure notifications. No issue/comment/email reporting is installed. Existing scheduled agent tasks may inspect these reports through their existing access. The CI and PR Integration Steward has only the bounded repair delegation above; the nightly workflow itself still defers conflicts.

Primary execution requires `--state-dir` and writes one atomically replaced, flushed JSON receipt per unique run outside the disposable Git object store. Fallback retains its Actions summary/log receipt. Both record lock ownership and preserve any integrated-but-unverified SHA. Receipt or cleanup failure never replays a remote mutation or rewrites published history.

`governance/repository-controls/nightly-integration-policy.json` binds the reviewed workflow, controller and lock-module bytes by SHA-256. The repository validator independently checks those bindings, the exact workflow inventory, manual-only trigger, owner/default-branch restriction, read-only repository token, and serialization envelope. Update the affected hashes deliberately when changing those files. Workflow and executor changes require focused tests and `python tools/prepare_commit.py --base origin/main --check --full` against the final staged snapshot.

GitHub's [Git reference API](https://docs.github.com/en/rest/git/refs), [ruleset behavior](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets), [ruleset-detail API](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset), and [PR merge API](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request) define the hosting behavior. The merge API's expected SHA binds the source; the strict no-bypass main ruleset also protects against a last-moment base update.
